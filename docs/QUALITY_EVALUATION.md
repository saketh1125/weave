The fixture at `tests/fixtures/documentation_quality.json` labels eight
independent examples for three existing surfaces: cited Q&A (`POST
/api/repos/{id}/ask`), generated code summaries (`POST
/api/repos/{id}/docs`), and documentation/code review (`POST
/api/repos/{id}/drift`, including optional behavioral review). The app's Q&A
response includes an answer and numbered candidate citations; docs generation
returns structured `summary`, `key_behaviors`, and `complexity_note`, plus
`context_complete`; drift returns `aligned`, `outdated`, or `unverified` items
with document/code source ranges. These interfaces do not currently share a
single quality-evaluation runner.

## Fixture cases

Each case provides its question/task, synthetic source text or a deterministic
source-construction recipe, expected facts, source path and line range for
citation, disallowed claims, and expected handling. The eight cases cover:

- A documented fact with a valid citation.
- A function return located beyond character 3,000, with a full-context summary
  expected to include it.
- A docs/code contradiction that must be surfaced with both sources.
- A conditional function with both branches preserved in its summary.
- A truncated source where the omitted return behavior must not be asserted.
- A historical runbook that must not be treated as the current contract.
- A qualified/conditional policy statement.
- A question for which the supplied evidence says nothing and abstention is expected.

The labeled source ranges are evaluator ground truth. Generated-doc API output
does not currently include citation ranges; for summary cases, use the ranges
to check grounding during review, not as an asserted response field.

Structured sources may use `construction` instead of `content`. Expand them
mechanically as `prefix + repeat_text * repeat_count + suffix`; preserve the
path as one source file. The late-fact Python function places `return 9` after
character 3,000 at line 262. Parse the expanded file and evaluate it as one
complete function, so the summary should mention that return value. This case
checks the current multi-section full-source path without turning the old
single-excerpt boundary into its expected behavior.

The excerpt case deliberately separates `sources` (the full synthetic file)
from `evaluation_context` (the shorter text actually supplied to the evaluator).
Its expected answer must be based only on that excerpt, which omits the known
`return 7` line. This is an evaluator-context contract, independent of how
production generation selects sections or reports coverage. The fixture
integrity test expands recipes and checks citation ranges; no prose recipe
should be interpreted as source text.

## Bounded protocol

The provider-free manifest is generated by `python scripts/evaluate_quality.py`.
It expands source recipes, validates unique paths and citation bounds, and emits
the fixture hash, labels, and source text with `quality_scores: null`. Use
`--output <path>` to save the manifest instead of printing it. This mode makes
no provider calls.

`--live` explicitly selects only `summary-fact-after-source-boundary` and
`summary-conditional-branch` through the current documentation-generation
prompt. Its default maximum is eight provider HTTP attempts; `--max-calls` may
lower that cap but cannot raise it. The runner reserves two attempts per model
chat invocation to account for the shared client's retry, stops after a
rate/quota error, and records actual raw summary outputs or sanitized errors,
model/version, fixture hash, and case IDs. It makes no automatic factuality
judgments. Live mode was not run while authoring this protocol.

1. Pin the checkout revision and fixture SHA-256 in the run notes. Read the
   expected labels before starting; do not edit labels after seeing outputs.
2. Use only the synthetic source texts in the fixture. Do not upload private
   repositories or send any source to a model provider. For a deterministic
   automated pass, stub retrieval/provider responses locally; this checks
   formatting, range mapping, truncation flags, and abstention plumbing only.
3. For a human quality pass, inspect each case's answer/summary/drift result
   against its labels. If testing a provider-backed implementation is later
   approved, run it only with these synthetic inputs and record provider/model,
   prompt/schema version, and date separately; provider results are not
   implied by this document.
4. Score each applicable dimension per case as pass/fail/not applicable:
   expected facts present; all factual claims supported; cited path/range
   actually contains the support; no forbidden claim; required uncertainty,
   contradiction, condition, historical scope, or abstention preserved.
   Count cases and failures, and list case IDs for each failure. Do not turn
   this eight-case contract check into a general accuracy percentage.
5. For `documentation_summary`, evaluate the exact source/context specified by
   the case: full expanded source for the late-return case, and only
   `evaluation_context.content` for the excerpt case. Do not substitute a
   production truncation policy for either fixture definition.
6. Report fixture-only checks separately from retrieval quality. To claim a
   retrieved citation, confirm that its content actually appeared in the
   selected evidence, not merely that the expected source exists in the
   fixture. A missing fact after the source limit should be unknown unless
   the answer path retrieved the full source independently.

For this micro-fixture, the contract gate is zero forbidden claims, correct
handling on all applicable cases, and citations that resolve to the labeled
source lines. Any missed expected fact is recorded as a failure. This is a
regression gate for these authored examples, not a release-quality threshold.
Report truncation/context completeness and provider errors independently from
factuality; valid JSON or an `aligned` label alone is not evidence of factual
quality. In particular, an `unverified` drift result is not a factual match.

## Limits and reporting

The cases are synthetic, authored from simple propositions, and not sampled
from user repositories. They provide no measured retrieval recall, model
factuality, citation precision, scanner performance, or representative
held-out estimate. The late-fact case exercises a fact beyond character 3,000;
it does not encode a limit on expected behavior. The excerpt case tests only
the provided excerpt by construction. Keep this fixture versioned and add new
cases before tuning against them, or create a new fixture version and preserve
prior results. Version 1 can remain unchanged because no outputs have been
evaluated against it.

Record each run as: checkout revision; fixture version and SHA-256; method
(manual or deterministic stubs); case counts by task; per-dimension pass/fail
counts and failing case IDs; and, only if used, provider/model and prompt/schema
versions. Do not describe this fixture as held out, representative, or as a
measured/provider result.
